# 个人量化平台项目宪章

## 核心原则

### I. 决策辅助，而非交易执行

系统 MUST 只提供数据、回测、信号、投资建议和实盘跟踪，不得直连券商或交易所执行交易。每条建议 MUST 明确关联策略版本、数据时点、目标标的、建议动作与生成时间，并保留“建议”与“实际操作”之间的区别。用户可以确认、拒绝或修正建议；实盘的持仓、现金和后续信号 MUST 以已确认或手工录入的实际操作为准。任何界面、通知和文档不得把回测收益或模型输出表述为确定收益。

理由：资金决策需要清晰的人在回路中，并且分析状态必须反映真实发生的操作，而不是系统曾经提出的建议。

### II. 时间一致、可复现的数据与回测

行情与基本面数据 MUST 标注来源、标的、频率、时区、交易日、可获知时间和数据身份；因子结果 MUST 可追溯到因子名称、应用发布版本、输入数据和计算时点。所有外部来源 MUST 先归一化到稳定的内部数据契约。回测与因子计算只能读取决策时点已经可获知的数据，MUST 防止未来函数、幸存者偏差和不明确的复权处理。相同应用发布、策略版本、参数、输入数据、费用模型与随机种子 MUST 产生相同结果。回测结果 MUST 保存上述输入身份、运行状态、关键指标及必要的审计信息，不得只保存最终收益值。

理由：无法说明“当时知道什么”和无法复现的结果，不具备投资决策价值。

### III. 契约驱动的可扩展性

数据源、文件导入器、因子、策略、通知渠道和调度任务 MUST 通过显式契约接入，领域逻辑不得依赖某个具体供应商、文件格式或传输协议。需要独立演进的数据协议、上传格式和策略 MUST 使用可识别的版本；因子由平台以程序内独立方法统一提供，随应用整体发布，不建立面向用户的独立版本、发布或页面管理流程。预设策略与用户策略 MUST 使用同一策略模板、生命周期和验证流程；策略版本一经用于回测或实盘即不可原地修改，变更 MUST 产生新版本。供应商原始字段、缺失值和异常 MUST 在适配器边界处理，核心领域仅消费规范化模型。

理由：多来源数据、平台因子与用户策略承担不同职责；显式契约可以避免供应商细节扩散，在保持因子发布方式简单的同时保证预设策略和自定义策略行为一致。

### IV. 领域核心与基础设施隔离

因子计算、组合状态、信号判定、回测推进和建议生成 MUST 可以在不启动 Web 服务、数据库、调度器、网络或消息服务的情况下运行。Flask、SQLAlchemy、MariaDB、ntfy、邮件和第三方数据接口属于可替换的基础设施适配器；它们不得成为领域模型的隐式全局依赖。时间、随机性、标识生成和外部 I/O MUST 可注入或由明确端口提供。

理由：隔离副作用既保护金融计算的可验证性，也使离线测试和替换基础设施成为可能。

### V. 风险导向的完全离线测试

自动化测试 MUST 不访问第三方服务、网络、中间件或真实持久化存储，也不得依赖真实时钟、未固定的随机数或开发者机器状态。外部边界使用内存实现、fixture、fake 或录制后脱敏且纳入版本控制的样本；测试 MUST 在任意顺序下可重复执行。测试与实现可以并行推进，不强制形式化的测试先行；覆盖率仅作诊断信息，不设盲目追求的统一百分比。优先验证资金与持仓演算、时间边界、防未来函数、数据归一化、策略契约、幂等性、失败恢复和权限边界。缺陷修复 SHOULD 添加能够复现该缺陷的回归测试。

理由：测试的目标是降低实质风险，而不是制造覆盖率数字；隔离外部依赖是快速、稳定反馈的前提。

### VI. 可审计、幂等且安全的运行

数据同步、回测、信号生成、通知和操作确认 MUST 使用稳定业务标识并支持安全重试；同一业务事件不得因重复调度或投递而产生重复建议、通知或账务变化。关键状态迁移 MUST 记录操作者或触发源、时间、前后状态和关联实体。密钥、令牌、邀请码和个人联系方式不得进入源码、日志、fixture 或错误响应。用户策略虽在受信任用户边界内，仍 MUST 明示其执行权限与资源风险，并与 Web 请求、调度器及密钥采用与部署场景相称的隔离；不得把“用户可信”解释为允许无边界的隐式权限。

理由：定时任务和消息投递天然可能重复，而动态策略代码具有高权限风险；二者都需要可追踪且可恢复的边界。

## 产品与技术约束

- 产品当前只处理低频行情，最细粒度为日线；任何高频、自动下单或券商接入需求都必须先修订宪章与架构。
- 前端基线为 TypeScript、React、shadcn/ui 与 Tailwind CSS；后端基线为 Python 3.12+、Flask、SQLAlchemy 与 MariaDB；ntfy 为默认推送适配器之一。偏离基线 MUST 在 feature plan 中说明原因、替代方案和迁移影响。
- API 与 worker 在开发、测试部署和生产等所有可运行环境中 MUST 连接显式配置的 MariaDB 并持久化业务状态，不得按环境自动回退到进程内或其他易失存储。自动化测试 MAY 在显式依赖注入下使用 fake/in-memory 端口实现；这类替身不得成为运行时配置选项。
- 平台为受控邀请制，不开放公共注册。认证、授权和数据隔离仍是必须验证的系统行为。
- 数据接口及上传格式 MUST 有版本化 schema、校验规则、错误报告和来源追踪；无效数据不得静默进入规范化数据集。
- 金额、价格、数量、收益率、时区、交易日历、复权方式、手续费与滑点 MUST 使用明确的数据类型和口径，禁止依赖浮点默认行为或环境默认时区。
- 机器学习因子 MUST 使用随应用发布的预训练权重，运行期只执行推断，不向用户提供训练、上传或模型管理功能。推断结果 MUST 可追溯到应用发布和权重身份；模型的离线训练与验证 MUST 遵守时间顺序，禁止以随机切分掩盖时间泄漏。
- 项目协作、面向用户的说明、进度反馈和文档默认 MUST 使用中文；仅在用户明确要求其他语言，或代码标识符、协议名称、业内术语等使用原文更准确时例外。
- 开发过程中确需访问国际网络时 MAY 使用本机 HTTP/HTTPS 代理 `127.0.0.1:7890`。该代理不得成为应用运行或自动化测试的隐式依赖，且不能用于绕过执行环境的权限、网络或安全策略。
- 快速测试 MAY 在用户显式开启时使用确定性 Mock 补足数据，MUST 标记补值、用途和输入身份；含 Mock 的结果不得作为实盘启动依据。正式回测与实盘 MUST 使用真实数据，不得补造缺失行情或基本面。快测及日线回测 MAY 使用当日开收盘均值作为模拟盘中报价，MUST 披露其包含收盘信息、仅用于近似模拟；其他历史与基本面查询仍遵守决策时点边界。
- Living Docs 位于 `docs/`，只描述当前系统真实状态；历史决策、讨论过程和未来设想分别进入 feature artifacts、ADR 或 issue，不得混入 Living Docs。

## 开发工作流与质量门禁

- 新能力或外部行为变化 MUST 依次形成可测试的 `spec.md`、通过宪章检查的 `plan.md` 和按依赖排序的 `tasks.md`，再进入实现；纯文档或低风险修复可按影响缩减产物，但不得跳过必要的行为说明。
- 每个需求 MUST 可由验收场景、契约测试、领域单元测试或明确的人工验证步骤证实。实现与测试可以在同一任务中完成。
- 代码评审 MUST 检查时间一致性、数据血缘、幂等性、策略版本不可变性、实际操作账本、安全边界、离线测试以及 Living Docs 同步情况。
- 合并前 MUST 运行受影响范围的格式化、静态检查与测试。全量命令由仓库 `AGENTS.md` 和开发文档维护；暂不可运行的检查 MUST 在评审记录中说明原因和风险。
- Git 使用小而可验证的提交；行为变化与对应测试、文档保持同一变更链路。分支、提交格式和钩子规则以 `docs/Git 协作规范.md` 为准，但不得与本宪章冲突。
- 设计优先选择满足当前需求的最小方案。新增服务、队列、缓存、通用框架或供应商耦合 MUST 在 plan 中说明当前必要性、失败模式和退出路径。

## 治理

本宪章是项目工程与产品边界的最高约束；`README.md`、`AGENTS.md`、Living Docs、feature spec、plan、tasks 和代码与其冲突时 MUST 以本宪章为准并修正冲突项。

修订宪章 MUST：说明动机与受影响产物；同步相关模板、规范和 Living Docs；为已存在的不兼容实现提供迁移或明确的技术债计划。版本采用语义化规则：删除或重新定义原则、放宽不可妥协约束为 MAJOR；新增原则或实质扩展约束为 MINOR；澄清措辞且不改变义务为 PATCH。

每个 feature plan MUST 包含宪章符合性检查；评审者对 MUST 条款逐项确认。无法立即满足的条款不得静默豁免，必须记录范围、风险、责任人和截止条件，并在合并前获得项目维护者明确批准。
