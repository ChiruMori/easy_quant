# 实盘分析性能与租约

实盘分析原先无条件准备全市场历史行情：未声明窗口、未调用因子的网格模板也默认读取 250 个交易日，再把全部行情编码发送给策略子进程。因此首次实时价格请求之前可能已经耗费数分钟；回测复用已预热的子进程，并不经过相同路径。旧日志只能证明这段等待位于任务领取与报价响应之间，不能据此精确分摊数据库、编码及网络耗时。

当前按策略代码使用的数据准备输入：

- 纯盘中报价策略（包括网格模板）不读取日线。已有持仓一次批量获取当前报价，其他价格按策略请求获取，本轮缓存复用。
- 只读取股票池、持仓等且无历史访问的策略准备上一交易日及当日的日线输入，不再默认读取一年。
- 调用因子、库函数、直接访问 `data`、历史接口，或显式声明 `HISTORY_TRADING_DAYS` 的策略保留窗口预热。分析采用整份代码的保守判断，跨钩子共用函数或动态因子调用仍预热，不执行用户代码来推断依赖。

日线继续按可获知时间过滤；盘前、盘中不暴露当日收盘，因子保持即用即算。策略版本直接按ID读取，不遍历所有策略。无需重建K线、实盘或策略数据。

实盘分析只将通知创建为持久投递记录并加入现有 `notification-delivery` 队列，渠道网络请求由通知任务执行。建议、状态和阶段完成标记先提交，通知失败不会重新执行策略；已有outbox在重试时幂等恢复。其他业务调用通知的默认发送方式不变。

## 日志及耗时

`实盘分析阶段` 记录实例、钩子、已完成阶段、该阶段秒数、累计秒数及下一阶段。阶段覆盖待发通知入队、状态、版本、行情、其他数据集、策略、建议保存、新通知入队。`实盘行情输入` 记录历史天数、行数、股票池数量及 `quote_only`。`实盘报价开始/结束` 单独记录请求数量和秒数；报价耗时包含在策略阶段中，不能重复累加。任务成功结果保存 `timings` 和 `elapsed_seconds`。

实盘子进程输入的JSON编码、管道写入与读取共用超时截止时间，管道阻塞不会绕开策略超时；宿主同步报价仍受行情适配器自身网络超时约束。策略阶段失败可根据最后一条 `next` 和报价日志定位等待位置。实时报价来源的短超时、按轮重试和耗尽告警见[实盘报价容错与告警](实盘报价容错与告警.md)。

离线回归中，网格模板使用真实受限子进程、fake报价和内存仓储，零次日线读取，单标的报价一次，完整分析约0.23秒；双持仓报价一次，完整分析约0.22秒。这些数据验证输入路径，不能替代生产数据库、磁盘、外部报价和通知队列的端到端测量。

部署后重启API和worker，用原实盘的下一次盘中任务检查 `quote_only=True rows=0`、报价秒数和总秒数，以10–20秒目标验收。外部报价慢时可由报价开始/结束日志单独定位；已有建议在通知任务执行前即可查看。

## 长任务租约

worker原先只在领取时设置5分钟租约，6分钟任务确实可能在执行中被再次领取。当前执行期间每30秒后台续租，使用独立数据库会话和短事务；较短租约的续租间隔最多为租约时长的三分之一。续租日志同时提供长阶段仍在运行的观察信号。

续租及完成写入在数据库中原子检查任务ID、`running`状态、持有者、领取次数及租约尚未过期。即使新旧进程使用相同worker标识，旧领取次数也不能覆盖新的执行状态。过期租约不能被旧执行续活；续租失败会记录日志，失效结果被丢弃，进程退出后仍按到期租约恢复任务。此防护针对任务状态写入；不会强制中止任意宿主I/O，实盘建议和阶段仍依靠已有事务、状态修订号及业务键防止重复提交。
