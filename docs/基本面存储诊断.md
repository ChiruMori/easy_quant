基本面是宽 JSON，日线是紧凑数值列，两者不能按行数比较体积。五只股票的有界样本中，三表单条约2.9–3.4 KB、指标约5.6 KB、主营约2.3 KB；原始科目、标准字段、单位及版本元数据逐行保存。以内容哈希作为聚簇键的分散写入也不具备顺序追加的页密度。上述证据说明宽载荷和聚簇数据页是主要成本，244 MiB二级索引和5 MiB data_free均不能解释全部数据区；不能把7.32 GiB都归因为重复状态或可直接回收的碎片，也不能凭有限样本精确推断全表逻辑字节及各数据集占比。

当前新写入大载荷使用无损 zlib/base64 JSON 编码，SQL所需来源、报告期、范围、分类、项目和登记日仍为顶层元数据。读取同时兼容旧 JSON；API和worker须同步升级，旧代码不识别新压缩记录，回滚代码时须保留解码兼容；页面、策略和来源完整字段不感知压缩，不改变内容身份与首次可见时间。八类财务数据各取200条真实记录，在客户端验证无损往返：原载荷合计5,573,116字节，新编码2,976,146字节，样本减少约46.6%；这是载荷对比，不是磁盘回收承诺。重复财务内容不重写旧行，因此上线后旧数据不会自动变小。

证券状态只在代码、名称、交易所、上市日期、交易状态、ST标记改变，或来源明确提供的停牌区间/人工依据更正时新增快照，日期、来源切换及重复停牌观测不单独形成版本。状态回变仍保存新事件。已有重复快照只读折叠，保留每段状态首次可见时间，不改真实库；股票详情计数与分页、策略输入一致。缺失上市日期的来源不会抹掉已有上市日期。

存取检查：单股指标分页 EXPLAIN 命中 `(symbol,dataset_key,available_at)`，range访问、估算23条，无 filesort；未证明所有查询在全市场运行中都达标。财务版本检查仅读取目标股票和报告期元数据；保存批次最多500条。报表仅查单股近五年当前可见数据、最多5001个版本并明确报超限，不把完整原始科目返回图表。回测存在性预检改为 `LIMIT 1`，避免为判断非空加载整个数据集；回测、快测与实盘读取先在SQL约束可见时间，读取分批，不把未来记录装入内存。全市场策略本身确需的历史仍有内存成本，不宣称已改成完全流式基本面引擎。

可复用只读命令：

uv run --project backend python backend/tools/measure_market_record_compression.py

本次没有执行 UPDATE、DELETE、ALTER、OPTIMIZE 或旧数据重编码。要回收已有磁盘，需要另外安排可备份、可核验、可恢复的旧记录重编码和表空间维护窗口；这不属于当前运行行为，也没有自动执行入口。
